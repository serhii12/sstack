# Triage comments

The three comments that [SKILL.md](SKILL.md) posts: the Agent Brief, the Triage Notes and the Triage Decision. Read this file before step 4 of the skill.

Contents:

- The AI line
- Agent Brief: rules, template and an example
- Triage Notes
- Triage Decision

## The AI line

Every comment that triage posts starts with this line. The check script looks for it right above each triage heading.

```markdown
> *This was generated by AI during triage.*
```

## Agent Brief

The brief is the ticket. After you post it, the brief is the contract. The original report and the talk under it are only background. `/build` reads the brief and works from it.

Rules for a brief:

- Make it last. The issue can wait for weeks, and the code changes in that time. Name types, function signatures, config shapes and behavior. Do not name file paths or line numbers. They go stale.
- Describe behavior. Say what the system must do. Do not give steps such as "open this file and add a field". The agent reads the code fresh and makes its own choices.
- Give acceptance checks that can fail. Each check names what to observe and where. Each check fails before the work and passes after it. "Triage works correctly" is not a check.
- Name what is out of scope. This stops the agent from adding things nobody asked for.
- For a pull request, say what is left to do on the diff: finish it, close gaps, or answer review points. The agent does not build it again.
- For `ready-for-human`, add the `Why a human:` line. Name the judgment, the access or the manual test that an agent cannot do.

Template:

```markdown
> *This was generated by AI during triage.*

## Agent Brief

Category: <bug | enhancement>
Summary: <one line: what must happen>
Why a human: <only for ready-for-human>

### Current behavior

<What happens now. For a bug, the broken behavior. For an enhancement, the current state.>

### Desired behavior

<What happens after the work. Name the edge cases and the error cases.>

### Key interfaces

- `<TypeName>`: <what changes and why>

### Acceptance checks

- [ ] <What to observe, and at which test boundary. It fails before the work and passes after it.>

### Out of scope

- <A thing that this ticket does not change>
```

A good bug brief:

```markdown
> *This was generated by AI during triage.*

## Agent Brief

Category: bug
Summary: The cart total ignores the discount code when an item has a quantity above 1.

### Current behavior

`cartTotal(items, code)` applies the discount only to the first unit of each item.

### Desired behavior

The discount applies to every unit. A code that does not exist changes nothing.

### Key interfaces

- `cartTotal(items, code)`: the return value changes. The signature stays.

### Acceptance checks

- [ ] `cartTotal` returns 36 for two hats at 20 with the code `SAVE10`.
- [ ] `cartTotal` returns 40 for the same cart with an unknown code.

### Out of scope

- New discount codes.
```

A bad brief says "the triage thing is broken, look at the main file around line 150". It has no category, no current and desired behavior, no checks and no scope. It names a path and a line that go stale.

## Triage Notes

Post these for `needs-info`. Put every settled point under "What we know", so the work is not lost. Each question is specific. "Please give more information" is not a question.

```markdown
> *This was generated by AI during triage.*

## Triage Notes

### What we know

- <a settled point>

### What we still need from you

- <a specific question for the reporter>
```

## Triage Decision

Post this for `wontfix`, then close the issue.

```markdown
> *This was generated by AI during triage.*

## Triage Decision

Decision: wontfix, <already implemented | rejected bug | rejected enhancement>
Reason: <why, in one or two lines>
Where: <for already implemented: the behavior and where it lives. For a rejected enhancement: the `.out-of-scope/<concept>.md` file.>
```

For a rejected bug, explain the reason politely.
